## How seating methods work

Generate tournament seating on **Manage games** in the <a href={env.urls.forseti}>administration panel</a>.
For the complete sequence, see the <a href='/en/forHosts#tournament'>tournament administrator guide</a>.
Each table needs four players, or three in a sanma event. Check the included player list before generation.

### Random seating

Players are shuffled into tables without grouping them by their positions in the standings. This is the available
automatic method for the first session, since it does not require earlier results. Predefined events can instead
use their script from the first session.

The generator tries several shuffled arrangements and compares their repeat encounters with previous seatings.
It keeps the best arrangement it finds, then assigns initial winds according to the event's wind shuffle mode.
This means the result is not a completely unrestricted random draw when playing history is available.
Repeat opponents are still possible, especially later in the tournament; this method does not guarantee
either new opponents or opponents with similar ratings.

### Swiss seating

Swiss seating uses current standings and the history of encounters. It tries to put similarly ranked players
together while reducing repeat opponents. Those goals cannot always be met simultaneously, so a repeated
encounter is not necessarily an error. It becomes available after previous games; approve their results before
generating the next session.

#### How the Swiss algorithm builds tables

An **encounter** means that two players have already played at the same table. Playing together twice counts
as two encounters, so the generator considers the number of previous meetings, not just whether a pair has met.
The simplified procedure is:

1. Start with the current standings and the history of who played whom. Select the highest-rated player
   who has not yet been seated and put them at the next table.
2. Look for the highest-rated available player who has not played with anyone already at that table.
3. Repeat that selection until the table has four players, or three for sanma. A candidate is checked against
   every player already selected for the table, not only its first player.
4. Set those players aside and start the next table with the highest-rated remaining player.
5. If a choice prevents the remaining tables from being completed under the current encounter limits,
   backtrack and try another candidate. The first promising table is therefore not necessarily the final one.
6. If avoiding repeats is no longer possible, allow repeat encounters. Prefer candidates with fewer previous
   meetings with the selected players, then higher-rated candidates among those choices.
7. Continue until everyone is seated, then assign the initial winds using the selected wind shuffle mode.

The search is combinatorial: trying every possible seating would become impractical as the player count grows.
The generator limits the search effort by relaxing encounter constraints as the search becomes more expensive.
It does not guarantee a globally optimal seating or the absolute minimum number of repeated encounters.

Later tables have fewer available players to choose from, so avoiding repeats can be harder there. The actual
history matters more than the table count alone: a power-of-two table count is not a guarantee of no repeats,
and other table counts are also supported.

### Interval seating

Interval seating groups players by their positions in the current standings, using the selected spacing.
It does not use encounter history to avoid repeated opponents. It becomes available after previous games.

- Interval **1**: ranks 1–2–3–4, then 5–6–7–8.
- Interval **2**: ranks 1–3–5–7, then 2–4–6–8.
- Larger intervals spread ranks farther apart. The remaining players form the later tables.
- Sanma tables contain three players: for example, interval 1 starts with 1–2–3 and interval 2 with 1–3–5.

#### How interval groups and remaining tables are formed

The interval is a positive whole number. For four-player tables, an interval of 3 forms groups of three tables
from blocks of 12 players in the standings. The first block is:

- Table 1: ranks **1–4–7–10**.
- Table 2: ranks **2–5–8–11**.
- Table 3: ranks **3–6–9–12**.

The next three tables use ranks 13–24 in the same way. Tables are ordered by their highest-ranked player.
Thus the interval spreads players within each block; it does not distribute the entire field evenly between
every table in the tournament.

If the table count is not divisible by the selected interval, players at the bottom of the standings who do not
fit a complete interval group are seated with **interval 1**. For example, with 16 players and interval 3,
the first 12 players form the three tables above, while ranks **13–14–15–16** form the remaining table.
If the interval is larger than the total number of tables, all tables use this fallback.

For sanma, each complete interval group contains three times the interval in players: interval 3 uses nine
players per group, and any remaining tables are also filled with adjacent ranks. Neither the regular groups
nor the fallback avoids previous opponents, so repeated encounters can be concentrated at the remaining tables.

### Predefined seating

Enable **Seating is defined in advance** in tournament settings, assign and save **Local IDs** on
**Manage players**, then enter the table plan on **Predefined seating**. Each line is a table of local IDs
separated by hyphens; a blank line starts the next session. Use four IDs per table, or three for sanma.

Set **Next session index** to the intended block (starting at 1), update the script and resolve validation errors.
On **Manage games**, **Next seating** generates that block. The index advances when the timer starts.
After session approval, generate the next block. When no blocks remain, add and validate more before continuing.
See the <a href='/en/forHosts#predefined'>predefined seating walkthrough and example</a>.

#### Combining a script with automatic seating

Predefined seating requires preparation: save the player-to-local-ID assignments and the complete table plan
before generating its first session. Automatic methods instead calculate each next seating from the registered
players, standings and playing history available at that moment.

Turning off **Seating is defined in advance** makes the automatic methods available; they use the event's existing
results and encounter history. If you later return to a predefined plan, check both the script and
**Next session index** carefully. The selected block must match the session you actually intend to play;
changing the seating mode does not construct a matching script or erase earlier games. Prepare this transition
in advance rather than switching modes during a session.

### Table groups and initial winds

The seating method chooses table groups. **Wind shuffle mode** determines the initial seats within those groups:

- **Random wind shuffle:** randomly assigns winds at each table.
- **Balanced wind shuffle:** tries to assign winds that each player has played less often.
- **Prescripted wind shuffle:** available for predefined events; follows the order in each script line,
  East–South–West–North (East–South–West in sanma).

Check the generated tables and winds at **Seating ready**. Use **Reset seating** to discard a mistake
before starting the timer. Once everyone is seated, **Start timer** begins all tables together.
